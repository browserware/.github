## Problem Statement

Browserware is building a modular ecosystem for intelligent browser routing across macOS, Windows, and Linux. The current repo already has the right crate split: detection, profiles, launch, rules, system integration, shared types, and CLI.

The product risk is positioning. Existing tools already handle consumer browser picking and URL routing well enough, especially on macOS. Browserware should not start by cloning Velja, Choosy, Browserosaurus, or Finicky. It should own the lower layer they do not expose cleanly: discovering every launchable browser context on a machine and launching it predictably from code.

## What Makes This Cool

The "whoa" moment is:

```bash
brw contexts --json
```

It prints every usable browser context on the machine: Chrome Stable / Work, Chrome Canary / Testing, Edge / Client A, Firefox Developer Edition / Default, Safari / default, and unknown registered handlers where metadata is partial.

Then:

```bash
brw open https://github.com --context chromium:work
```

It opens the URL in the right context without the user remembering bundle IDs, profile-directory names, executable paths, or OS-specific launch flags.

That is useful to developers, agents, scripts, tests, and later a GUI/default-browser shim. Same foundation, many surfaces.

## Constraints

- The first release must be CLI/library-first, not GUI-first.
- The crate architecture should stay modular. Libraries must remain useful standalone.
- Detection should stay discovery-first: enumerate registered system handlers first, then enrich known browsers with registry metadata.
- Browser profiles are not uniform. Chrome-family profiles, Firefox profiles, Safari, Arc/Dia spaces, and encrypted or inaccessible profile metadata all behave differently.
- Machine-readable output matters. This is a substrate for tools, not just a human menu.
- Cross-platform parity is a goal, but the first implementation can expose platform-specific capability gaps honestly.

## Premises

1. The first product should be a developer-facing CLI and library set, not a consumer default-browser GUI.
2. The core object should be a browser context target: browser app + engine/family + channel + profile + launch capability.
3. Browserware's first wow moment should be `brw contexts --json`, showing every launchable context on the machine in a stable, scriptable format.
4. The wedge user is a developer or automation-heavy builder with work/personal/client/agent browser contexts, not a normal Mac user who just wants links to open in Safari sometimes.
5. Rules matter, but they should sit on top of context discovery and launch. If discovery is wrong, rules are lipstick on a segfault.
6. The GUI/default-browser shim is still a good long-term product, but it should reuse the same substrate instead of driving the architecture.

## Search Findings

Existing tools show the consumer link-routing space is already real:

- Browserosaurus is an open-source macOS browser prompter that sets itself as the default browser and lets users pick an installed browser for clicked links. It is archived.
- Choosy supports browser prompts, rules, browser profiles for Chrome-family browsers, browser extensions, and URL-based automation.
- Velja supports browser rules, source-app matching, browser profiles, scripting via custom URL scheme, and profile-specific launching. Its docs call out hard browser-specific limits, including Arc/Dia not supporting Chrome's `--profile-directory` flag and Atlas storing profile names in an encrypted file.
- Finicky is the hacker/config-file version: JavaScript rules, URL rewriting, browser handlers, and browser extensions.
- Microsoft Edge policy docs show an enterprise variant of this problem: external links can prioritize an app-specified profile over the default external-link profile.

The search result changes the framing. Browserware should not claim browser/profile routing is untouched. The better opening is cross-platform, developer-grade context discovery and deterministic launch.

## Approaches Considered

### Approach A: Context CLI Wedge

Ship `brw contexts` and `brw open --context <selector>` as the first real product slice. It discovers browsers, enriches them with profile data where available, prints stable JSON, and launches a URL into a selected browser/profile.

Effort: M
Risk: Low/Med

Pros:
- Fastest useful thing to ship.
- Matches the existing crate layout cleanly.
- Creates a demo developers immediately understand.

Cons:
- Less visually impressive than a GUI.
- Profile support exposes browser-specific edge cases immediately.
- Rules remain basic at first.

Reuses:
- `browserware-detect`
- `browserware-profiles`
- `browserware-launch`
- `browserware-types`
- `browserware-cli`

### Approach B: Substrate First, CLI As Proof

Define a durable `BrowserContext` / `BrowserTarget` model first, then make detection, profile lookup, launch, and CLI all use it. The CLI becomes proof that the library architecture is right.

Effort: L
Risk: Med

Pros:
- Best long-term architecture.
- Makes the future GUI/default-browser shim much cleaner.
- Reduces the chance of baking CLI-only assumptions into core types.

Cons:
- Slower than a purely command-shaped implementation.
- More design pressure up front.
- Easy to over-model profile edge cases before real users hit them.

Reuses:
- All workspace crates, especially `browserware-types` as the contract layer.

### Approach C: Automation Gateway

Treat Browserware as infrastructure for agents, scripts, and dev tools. First-class JSON APIs, deterministic selectors, and commands like "open this URL in the best isolated work profile" matter more than human picker UX.

Effort: M/L
Risk: Med/High

Pros:
- Most differentiated from Velja, Choosy, Browserosaurus, and Finicky.
- Strong fit for AI/browser automation workflows.
- Could become the browser-context layer other tools build on.

Cons:
- Harder to explain to normal users.
- Needs crisp docs and examples.
- May be too narrow if the immediate goal is a broad user-facing app.

Reuses:
- Same substrate as Approach B, but biases toward machine-readable output, predictable selectors, and scripting contracts.

## Recommended Approach

Choose Approach B, with Approach A as the first milestone.

The product should be designed as a substrate, not a pile of CLI commands. But the first thing users should see is concrete:

```bash
brw contexts --json
brw open https://github.com --context chromium:work
```

That gives the architecture a spine and the product a demo. The CLI validates the core model. The core model keeps the future GUI/default-browser shim from becoming a separate product with separate logic.

## Engineering Review Decisions

- Scope split accepted during /plan-eng-review: PR1 should implement the `BrowserContext` model and `brw contexts` output only. PR2 should add `brw open <url> --context <selector>` launch behavior. This keeps context discovery usable even if profile-specific launch has browser-specific failures.
- Selector grammar accepted during /plan-eng-review: canonical selectors should be key-value, for example `family=chromium,browser=chrome,profile=work`. Compact aliases such as `chrome:work` can exist, but only as a convenience layer over the canonical form.
- Ambiguity handling accepted during /plan-eng-review: ambiguity is allowed and should be policy-driven. Initial strategies should include first match, warn/log, and error, configurable with flags. Machine-oriented paths should default toward explicit diagnostics; human convenience paths may choose first match when requested.
- Capability model accepted during /plan-eng-review: `BrowserContext` must expose capability flags in PR1, not defer them to launch. Include `discoverable`, `launchable`, `profile_launchable`, `requires_user_config`, and `limitations: Vec<String>` so contexts that can be discovered but not launched do not look equivalent to fully launchable contexts.
- Distribution scope accepted during /plan-eng-review: crates.io publishing is not in scope for PR1. Existing GitHub Release binary automation is enough for the first context-substrate implementation, but crates.io publishing must be captured as follow-up release work because the design promises `cargo install browserware-cli`.
- CLI organization accepted during /plan-eng-review: add small CLI modules for PR1, at minimum `commands/contexts.rs` and `output.rs`, so `main.rs` does not accumulate command orchestration, JSON shapes, and table rendering for every feature. Do not do a full CLI refactor in PR1 unless required by the contexts command.
- Test strategy accepted during /plan-eng-review: profile discovery must use deterministic fixtures, not whatever browser profiles exist on the CI machine. PR1 should include fixtures for Chrome-family `Local State`/profile directories, Firefox `profiles.ini`, no-profile/default-only browsers, and inaccessible or encrypted metadata cases.
- JSON stability accepted during /plan-eng-review: `brw contexts --json` is a public automation API and needs golden output tests, not just parseability checks. Public context structs also need serde round-trip tests.

## NOT in Scope for PR1

- `brw open <url> --context <selector>` launch behavior: deferred to PR2 so context enumeration can ship independently.
- Rules engine changes: deferred until discovery and context output are trustworthy.
- GUI/default-browser shim: long-term product surface, not part of the substrate PR.
- crates.io publishing workflow: existing GitHub Release binary automation remains, but `cargo install browserware-cli` publishing needs a separate release task.

## Open Questions

- What are the exact flag names for ambiguity handling, for example `--on-ambiguous first|warn|error` or shorter alternatives?
- Should `brw contexts` show ready-to-copy canonical selectors for each context in table output?
- Which profile metadata is safe to expose in JSON by default?
- How should Browserware represent contexts that are discoverable but not launchable, such as Arc/Dia profile-like spaces or browsers with encrypted profile names?
- Should the first milestone include rules at all, or only context enumeration and explicit launch?

## Success Criteria

- `brw contexts` returns a stable, documented list of browser contexts.
- `brw contexts --json` is machine-readable and suitable for scripts and agent workflows.
- `brw open <url> --context <selector>` launches into the intended browser context where the platform/browser supports it.
- Ambiguous selectors produce useful errors with suggested exact selectors.
- Unknown browsers remain visible rather than silently disappearing.
- Capability gaps are explicit: a context can be detected but marked as not profile-launchable.
- The same `BrowserContext`/`BrowserTarget` model can support a future GUI/default-browser shim.

## Distribution Plan

Browserware is a Rust workspace intended for crates.io distribution.

- Publish the library crates and `browserware-cli` to crates.io.
- Users install the CLI with `cargo install browserware-cli`.
- CI should build and test the workspace on macOS, Windows, and Linux.
- Release builds should use `--locked` to respect the committed `Cargo.lock`.
- Future GUI/default-browser app can live in a separate closed-source repo but must depend on the same open-source substrate contracts.

## Next Steps

1. PR1: Define the shared context model in `browserware-types`: `BrowserContext`, `ProfileRef`, `LaunchCapability`, `ContextSelector`, and explicit capability flags.
2. PR1: Extend `browserware-profiles` to return profile metadata with capability flags instead of pretending all browsers support the same launch behavior.
3. PR1: Add `brw contexts` with human table output and `--json`.
4. PR1: Document known browser limitations: Chrome-family `--profile-directory`, Firefox profiles, Safari limitations, Arc/Dia spaces, encrypted profile metadata.
5. PR2: Extend `browserware-launch` to accept a context target, not just an executable plus loose options.
6. PR2: Add `brw open <url> --context <selector>`, with exact-match behavior first and helpful ambiguity errors.

## Implementation Notes

PR1 should keep the CLI diff intentionally small:

- Add `commands/contexts.rs` for the `brw contexts` command.
- Add `output.rs` for reusable table/JSON/plain formatting helpers where they reduce duplication.
- Avoid a full migration of the existing `browsers` command unless the contexts command needs shared formatting.

PR1 tests should be fixture-driven:

- Add Chrome-family fixtures covering multiple profile directories and display names.
- Add Firefox fixtures covering `profiles.ini` with relative and absolute profile paths.
- Add default-only/no-profile cases for browsers such as Safari.
- Add inaccessible/encrypted/unknown metadata cases that produce capability limitations instead of panics or silent omission.
- Add CLI integration tests for `brw contexts --format json`, table output, plain output, and empty/no-context behavior.
- Add golden JSON tests for representative `brw contexts --format json` output and serde round-trip tests for public context structs.

## What I noticed about how you think

- You kept the CLI and GUI in the same product family instead of collapsing them into one thing. That is the right separation: one substrate, multiple surfaces.
- You accepted the search result changing the framing. That matters. The market already has pickers, so the product has to move down a layer where it can be more useful.
- You are building around a real developer annoyance: browser/profile context is state people carry in their heads because tools do not expose it cleanly.

## The Assignment

Before implementation, write three concrete user stories using real machine states:

1. A developer with Chrome Stable personal, Chrome Stable work, Chrome Canary testing, and Firefox Developer Edition.
2. An automation/agent workflow that needs an isolated browser profile for each project.
3. A future GUI/default-browser workflow that needs to choose a context automatically.

For each story, write the exact `brw contexts --json` shape you wish existed and the exact `brw open` command that should work. If those examples feel awkward, fix the model before writing code.
